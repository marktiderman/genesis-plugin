# Debrief — every cycle ends with one 1% better

An improvement loop without an artifact is a vibe. This makes the debrief real, durable, and fast:
four short lines and one concrete improvement, written down so the gains compound instead of
evaporating into chat.

## When to run

At every work-cycle close — a PR merged, a task done, a feature shipped, or a session ending with
work in flight. If you completed a unit of work, you owe a debrief before calling it done.

## The format — four lines

- **Well** — what worked, what to keep doing.
- **Didn't** — what broke, dragged, or surprised you.
- **Differently** — the change to make next cycle.
- **1% better** — ONE concrete, specific improvement.

The 1% is the line that matters, and it must be **an action, not a sentiment**. "Add a null check
to the migration template" is a 1%. "Be more careful with migrations" is a wish.

## Make it durable

Write the debrief where the work lives — the PR description, the issue, a decision log, a commit
message. **A debrief floating in a log disconnected from the work it debriefs is useless.** Bind it
to the thing it closes so someone reading that thing later finds the lesson attached.

## Give the 1% teeth

- If it's **actionable** — open an issue or a task so it actually happens. A written wish
  compounds nothing.
- If it's **a lesson** — save it somewhere durable that future work will actually read.
- If it's **neither** — it isn't a 1%. Find the real one.

## Three questions worth asking

Before closing, answer these out loud. They're where the honest material is:

1. **What did you not know that cost you time — and where should it have been written down?**
2. **How could the tools you used have been better?**
3. **What else should have been here that wasn't?**

If there's genuinely nothing, say so explicitly. A loop that's never fed can't get better.
